# COSMIC V6.2 — Manual staging activation playbook

Reviewed 2026-10-22 on `feat/cosmic-creative-economy-v6`.

## Readiness and review result

**Ready for manual configuration and staging acceptance; not yet provider-verified or live-ready.** The V6.2 implementation remains uncommitted. This readiness pass changed documentation only: no confirmed transaction-blocking code defect was found. Existing tests are not proof of a real Stripe payment, email delivery or MongoDB persistence.

Reviewed paths:
- `frontend/src/pages/api/services-inquiry.ts` → `server/engagementIntake.ts` → backend `/services/intake` → Opportunity; then `server/servicesInquiry.ts` → Resend.
- `frontend/src/pages/api/engagements/[[...path]].ts` → backend operator routes → JWT verification + database User + configured operator ID.
- `backend/lib/serviceEngagements.js`: approval, Checkout, authoritative retrieval, duplicate/out-of-order reconciliation.
- `backend/routes/services.js`: raw-body signed webhook mounted before JSON parsing, private routes and server-only intake.
- `backend/models/Opportunity.js`: embedded engagement, unique partial inquiry/session indexes. Mongoose's actual update casting preserves the null session/attempt defaults and numeric revision used by the flow.

Fresh verification: 18 backend tests, 9 frontend tests and TypeScript passed. Tests use fictional adapters, not a connected database/provider. The preceding V6.2 production build and lint passed with existing warnings; no runtime code changed in this pass. Do not use the temporary port-3110 fixture for acceptance: it mocks persistence and payment.

### Activation blockers, not new feature requests

- Stripe sandbox credentials and webhook endpoint/listener must be connected to the same account/environment.
- An isolated MongoDB database and an authenticated active operator must be configured.
- Both frontend intake variables must be set; leaving both absent deliberately retains V6.1 email-only behavior.
- Resend must accept the configured sender and controlled recipient.
- The webhook must use **snapshot** payloads, not thin events. It lives on the Express backend, not `/api` on the Next frontend.
- Live keys are intentionally rejected. Swapping to `sk_live_…` is not a supported activation procedure.

If testing deployed later, the current repository uses Next/Vercel and Express/Render conventions: frontend variables belong to the staging frontend project/environment; backend variables belong to the staging backend service. A Vercel-only deployment cannot receive the implemented Stripe webhook. A preview-login wall must not intercept the backend webhook. No hosting changes or deployments are performed by this guide's author.

## 2. Prepare accounts and decisions

Required:
1. Stripe account with a selected sandbox/test environment and permission to manage its API keys and webhook destinations.
2. MongoDB Atlas project/database (or isolated local MongoDB), a staging-only database user with read/write and index-creation permission, and allowed backend network access.
3. Existing Google and/or GitHub OAuth applications configured for the test frontend; use dedicated test accounts. Current auth source declares both providers. Preserve working provider configuration; configure both if testing both buttons.
4. Resend account, a permitted sending identity and an inbox you control. No real customer's email address is used.
5. Optional established scheduling provider account/link. It is not required to prove payment.

Decide before the fixture: operator identity, a fictional $150 USD total, scope/deliverables, a fictional agreement date, controlled inboxes and who will perform the test. Before live use, additionally decide service duration, availability/time zone, cancellation/refund terms, tax treatment, business/support identity and data retention. The code does not decide these for you.

## 6. Configure Stripe test billing

In Stripe's account picker, select the intended sandbox/test environment. Under Developers/Workbench → API keys, copy that environment's **secret test key** into backend `STRIPE_SECRET_KEY`. It must begin `sk_test_`; this implementation rejects `sk_live_` and restricted `rk_` keys. No publishable key or Stripe.js integration is needed because the browser opens a hosted URL.

Keep the same sandbox selected for Checkout inspection, webhooks and CLI authentication. Do not create catalog Products/Prices or a reusable Dashboard Payment Link for this flow: COSMIC supplies the approved quote to Checkout. Do not substitute a manually created payment for the COSMIC session.

The implementation pins API requests to `2025-03-31.basil`, uses USD/card-only Checkout and enables a **post-purchase invoice**. It does not create an invoice due before payment. Review test business branding/support details and invoice settings in Stripe; do not imply legal/tax configuration has been completed. For automatic real-payment receipts the relevant dashboard area is Settings → Business → Customer emails; test receipt email may require a manual Dashboard send to your controlled inbox. Missing email alone is not evidence that payment failed.

Restart backend. The operator page should say Stripe test billing configured. This only checks key shape; a successful Checkout creation is the first authenticated Stripe API verification.

## 7. Connect the signed webhook — choose ONE transport

Required event types:

```text
checkout.session.completed

checkout.session.async_payment_failed
checkout.session.expired
charge.refunded
charge.dispute.created
charge.dispute.closed
```

### Local acceptance (no deployment)

Install the official Stripe CLI if needed, run `stripe login`, and select/verify the same sandbox as the backend key. Never use `--live`.

```sh
stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,checkout.session.expired,charge.refunded,charge.dispute.created,charge.dispute.closed --forward-to http://localhost:4000/services/webhook
```

Enter the listener's displayed `whsec_…` secret directly into backend `STRIPE_WEBHOOK_SECRET`; restart backend and keep the listener running. Do not use a Dashboard destination's signing secret for CLI deliveries. If the listener changes its secret, update and restart again.

### Already-provisioned hosted staging alternative

Stripe Workbench → Webhooks → Create an event destination → **Your account** → **Snapshot** payload → select API version `2025-03-31.basil` and the events above → Webhook endpoint → `https://<staging-backend-host>/services/webhook`. Save its signing secret in the staging backend environment, then restart/redeploy that staging service yourself when authorized.

Do not choose Thin, Connected accounts, production frontend, `/graphql` or frontend `/api/engagements`. Do not run CLI and Dashboard deliveries to the same backend with two different secrets: this implementation accepts one signing secret.

Success: the real fixture transaction's `checkout.session.completed` event reaches this route with HTTP 200. A generic `stripe trigger` fixture may test transport but does not correspond to a COSMIC engagement and cannot prove the lifecycle.

## 9. Duplicate webhook and access checks

**Hosted endpoint:** in the sandbox Workbench event/delivery details, resend the same successful fixture event twice. Both deliveries should succeed and leave one Opportunity, one Checkout Session, the same paid state and no automatic scheduling/delivery or extra messages. The verification timestamp/revision may advance; that is expected reconciliation, not duplicate fulfillment.

**Local-only alternative:** use the actual event ID from the CLI and the following locally re-signed replay. This tests repeated delivery of the same provider event to the handler; it is not a second provider-originated delivery. The original CLI event must already have passed step 8. Run from `backend` with staging configuration and the CLI signing secret. Supply only the non-secret event ID when prompted by your shell workflow; never paste keys into the script. No live events are permitted.

```sh
# Replace with the actual fixture event ID (not a secret), in this terminal only.
export TEST_STRIPE_EVENT_ID=evt_REPLACE_WITH_FIXTURE_EVENT
node <<'NODE'
require('dotenv').config();
const crypto = require('node:crypto');
(async () => {
  const key = process.env.STRIPE_SECRET_KEY;
  const secret = process.env.STRIPE_WEBHOOK_SECRET;
  const id = process.env.TEST_STRIPE_EVENT_ID;
  if (!key?.startsWith('sk_test_') || !secret?.startsWith('whsec_') || !/^evt_[A-Za-z0-9]+$/.test(id || '')) throw Error('Check local test configuration.');
  const response = await fetch('https://api.stripe.com/v1/events/' + id, {
    headers: { Authorization: 'Bearer ' + key },
  });
  if (!response.ok) throw Error('Test event retrieval failed.');
  const event = await response.json();
  if (event.livemode !== false || event.type !== 'checkout.session.completed' || !event.data?.object?.metadata?.engagementId) throw Error('Use the actual COSMIC test Checkout event.');
  const body = JSON.stringify(event), t = Math.floor(Date.now() / 1000);
  const hash = crypto.createHmac('sha256', secret).update(t + '.' + body).digest('hex');
  for (let i = 0; i < 2; i++) {
    const r = await fetch('http://localhost:4000/services/webhook', {
      method: 'POST', headers: { 'Content-Type': 'application/json', 'Stripe-Signature': `t=${t},v1=${hash}` }, body,
    });
    console.log('Replay', i + 1, 'HTTP', r.status);
    if (!r.ok) throw Error('Replay failed; inspect status without sharing secrets.');
  }
})().catch(() => { console.error('Replay did not complete; check test configuration and endpoint.'); process.exitCode = 1; });
NODE
unset TEST_STRIPE_EVENT_ID
```

Additional checks:
- Signed-out browser visits frontend `/api/engagements`: HTTP 401, no records.
- Unrelated active staging creator visits the same API: HTTP 403, no records. A different admin is also not the configured operator. A signed-out `/creator/engagements` shows the normal sign-in gate.
- On the backend, `GET /services/` without bearer authentication returns 401. `POST /services/intake` without the server secret returns 403.
- A POST to `/services/webhook` with an empty JSON object and no Stripe-Signature returns 400 once the webhook secret is configured. No payment state changes. Do not weaken signature checking to resolve an error.
- A declined or abandoned Checkout remains unpaid, with no scheduling/delivery changes. An expired session becomes expired; this release intentionally has no replacement-session action. Finish the primary fixture in the same test session, within 23 hours of initial creation.
- Do not create live-mode events to test rejection. The automated tests cover live-key/event rejection with fictional values.

## 10. Diagnosis without exposing secrets

| Symptom | Check / safe next step |
|---|---|
| No durable record but inquiry email succeeds | Both frontend intake settings were probably absent, activating V6.1 compatibility. Set both, restart, and use a new fictional inquiry. |
| Saved inquiry, email unconfirmed | Inspect Resend acceptance/logs, sender permission and recipient. Keep the same form open and retry unchanged. Do not repeatedly reload and submit: a new mounted form has a new inquiry UUID. |
| Inquiry storage 503 | Check backend health, matching intake secrets, operator ID, database permissions/index creation, URL without `/graphql`; cold-start latency can exceed the 8-second intake timeout. Warm staging backend and retry unchanged. |
| Operator 401 | Sign in again; shared NEXTAUTH_SECRET, session expiry and OAuth callback must agree. Never paste cookies/bearer tokens into chat. |
| Operator 403 | Check actual database `_id`, role and creatorStatus; do not substitute OAuth subject. On POST, ensure exact origin/proxy HTTPS forwarding matches the frontend host. |
| Stripe not configured | Backend needs `sk_test_` from the same sandbox; restart backend. A restricted `rk_` or live key is intentionally rejected. |
| Stripe request 502 | In Stripe Workbench API request logs, inspect the sanitized error code/message: key/account permissions, invoice/account settings, request validity or network failure. Retry unchanged. Do not share full request bodies, auth headers or client context. |
| Webhook 400 signature | Correct transport's whsec secret, unchanged raw body, synchronized server clock, snapshot event and test mode. CLI and Dashboard secrets differ. |
| Webhook 401/redirect/404 | Wrong endpoint or hosting protection. Route is backend `/services/webhook`, not frontend; it uses signature authorization and must be reachable without browser login. |
| Webhook 409 | Quote/reference mismatch or concurrent reconciliation. Refresh and reconcile. Inspect only fixture IDs/amount/currency; do not bypass checks or manually mark paid. |
| Webhook 503 | Missing secret/Stripe config, backend/database failure or event before session persistence. Restore config, then resend the original event or reconcile. |
| Stripe paid; COSMIC unpaid | Confirm same sandbox, subscribed event, delivery HTTP status and saved cs_test ID. Reconcile to recover. A successful manual reconciliation alone does not prove webhook delivery—finish the webhook check too. |
| Paid but invoice ID initially absent | Check Stripe's invoice generation, then reconcile; receipt/invoice delivery is separate from payment verification. |
| No receipt email | Test receipts may require manual Dashboard sending. Inspect payment/invoice objects first; never make another payment just to get an email. |
| Attempt older than 23h with no saved session | Stop. Search Stripe test request/session records using engagement metadata. There is no safe automatic replacement/recovery UI in this release; do not clear fields or create another charge blindly. |
| Scheduling is unconfigured | Optional HTTPS provider page is missing; payment can still be verified. Do not pretend availability/invitations are automated. |

Share only route, HTTP status, sanitized error code, and fictional test IDs if needed. Never share env files, API keys, whsec values, database URIs, cookies, payment links tied to real clients or full logs. Existing backend startup logs include database-target information; redact before sharing.

## 12. Live readiness and later scale

Before real payments: complete this acceptance; authorize a bounded code/configuration pass for explicit live-mode support (currently rejected); verify business account/identity, invoice/tax/refund/cancellation policies, monitored email/webhook failures, retention/privacy and a safe expired-session/reconciliation procedure.
